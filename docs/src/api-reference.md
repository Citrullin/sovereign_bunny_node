# Rust API Reference

The Rust API reference is generated by `cargo doc` from the `///` and `//!`
doc-comments in the source code. Every public type, function, and constant is
documented with:

- **What it is** — the type's role in the architecture
- **Why it exists** — the invariant or threat it enforces
- **Stub Status** — clearly marked when implementation is incomplete, with
  the exact production requirements listed inline

## Generating the docs locally

```sh
cargo doc --workspace --no-deps --open
```

The output is written to `target/doc/`. The main entry points are:

| Crate | Entry point | Key types |
|---|---|---|
| `sovereign-consensus` | `sovereign_consensus` | `ValidatorRegistry`, `execute_lattice_block`, `finalize_epoch` |
| `sovereign-identity` | `sovereign_identity` | `SovereignDidDocument`, DID resolution |
| `sovereign-crypto` | `sovereign_crypto` | `SignatureScheme`, `verify_signature`, PQ key types |
| `sovereign-ssz` | `sovereign_ssz` | SSZ encode/decode, signal types |
| `sovereign-node` | `sovereign_node` | Node startup, RPC server |

## Relationship to this book

The architecture chapters explain *why* the types exist. The API reference
explains *what* they are. Each rustdoc comment links back to the relevant
architecture chapter where the design rationale lives. The
[Implementation Status](implementation-status.md) page gives the production
readiness of every component.

## Stub Status convention

Components that are stubs or work-in-progress carry a clearly marked section
in their rustdoc:

```
# Stub Status

> ⚠️ Work in Progress — …description of what is missing…

# Production Requirements

- Requirement 1
- Requirement 2
```

This convention is consistent across all incomplete components so that
tooling can search for `# Stub Status` to produce an automated gap report.
